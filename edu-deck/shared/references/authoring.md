> **기준 문서**: 저작 에이전트의 권한·재료 사용 방식·품질 판단을 한 곳에 모은 기준이다. 다른 문서는 재료·절차·계약을 정의하고, 이 기준과 충돌하면 이 문서가 이긴다.
> **로드 시점**: 새 덱·새 편 저작을 시작할 때 한 번, 그리고 재료를 고르거나 검사 결과를 해석할 때 다시 본다.

# 저작 권한과 품질 판단 (authoring)

## 1. 다른 문서와의 관계

| 문서 | 소유 영역 |
|---|---|
| `edu-deck/SKILL.md` | 진입 판별·팩/legacy 경로 결정·자유/가이드 모드 진입 |
| `composition.md` | 내용 구성 원칙·legacy 줄거리와 유형표·노트·자습 데이터 |
| `layouts.md` | 아키타입 조각·변형·표지 계약 |
| `resource-packs.md` | 팩 선택 계약·생성기·팩 덱 표현 계약·완료 판단 |
| `design.md` | 장의 배치·강조·밀도·색 판단 기준 |
| `expression.md`·`classes.md`·`diagrams.md`·`icons.md` | 문장·색·글자·클래스·도식·아이콘 문법 |
| solo·series `SKILL.md` | 절차(단계별 작업 순서)와 보고 |

## 2. 내용과 학습 목표가 재료보다 앞선다

저작은 아래 순서로 흐른다. 재료(조각·템플릿·카탈로그)는 이 흐름의 한 단계에 등장할 뿐이다.

1. 학습 목표·청중·가진 자료를 정한다(brief).
2. 교육 뒤 학습자가 해낼 행동을 정한다.
3. 장별 핵심 메시지와 메시지 사이 관계를 짠다(outline).
4. 메시지를 표현할 재료를 검색·선택한다.
5. 재료 사용 4방식(3절) 중 내용에 맞는 방식을 고른다.
6. 표지와 핵심 장 1~2장을 먼저 조립·렌더해 방향을 확인한다.
7. 나머지 장을 만들고, 전체 검증(6절) 뒤 수정·최종한다.

- **조각·템플릿의 종류에 내용을 억지 맞추지 않는다.** 아키타입 표·흐름 단계·변형 목록은 메시지를 놓는 자리 후보일 뿐이다. 내용이 어느 조각과도 맞지 않으면 새로 설계한다(3절).
- 벌어진 시간·활동·확인은 내용이 요구하는 만큼 둔다. 장 수 비율·파트 비율은 참고값이고, 실제 학습 목표와 증거가 먼저다.

## 3. 재료 사용 4방식 — 모두 동등한 정상 저작

| 방식 | 언제 | 예 |
|---|---|---|
| 그대로 사용 | 조각·템플릿이 내용과 그대로 맞을 때 | quiz-ox 조각에 문제만 넣기 |
| 변형 | 구조·비율·강조·항목 수를 내용에 맞게 바꿀 때 | tile-grid 카드를 4×2→2×3으로, 강조 색과 그림 자리 바꾸기 |
| 조합 | 둘 이상 재료를 결합할 때 | mapping 골격 + worked-example 포인트 리스트 |
| 새로 작성 | 재료로 표현하면 왜곡되거나 전달력이 떨어질 때 | `src/` 안에서 셸 클래스로 직접 설계 |

- 특정 방식을 우대하거나 의무화하지 않는다. "새로 설계한 비율", "재료 수정량"을 품질 지표로 쓰지 않는다 — 품질은 산출물이 학습 목표를 전달하는가로 판단한다(6절).
- 카탈로그(조각·표지 변형·테마·arc)는 실패 폴백이 아니라 출발점 재료다. 4방식 어느 쪽으로든 쓸 수 있다.

## 4. 작업 덱에서 고칠 수 있는 것과 보호 계약

작업 폴더의 `src/*.html`·`src/*.css`·`src/*.svg`는 저작 에이전트의 작업대다. **고칠 수 있는 것:**

- HTML 정보 구조와 장 배치 — 카드·그림·제목의 위치·비율·항목 수.
- 덱 전용 디자인 클래스를 작업 폴더 안에서 정의·추가하는 것(예: `.lesson-panel`).
- SVG·도식·시각 표현, 강조·여백·읽기 순서.

**보호하는 것(고치지 않는다):**

- 엔진·셸·검사기가 읽는 공개 속성과 계약: `data-step/add/only/lit/until`·`data-archetype`·`data-key`·`data-src`·`data-variant`·`.chk` 구조·`aside.notes`·`.fact`·`.chk-fb/go/again`(엔진 생성)·st-* 클래스·localStorage 키·`window.EDU_STUDY/deckGo/deckInfo`.
- 퀴즈·확인 문제·발표자 노트·출처·단계 공개의 실행 계약.
- 공용 원본(`assets/`·`shared/`·생성 셸) — 작업 폴더가 아니라 스킬 설치본이다. 스킬 자체의 CSS·JS·조각 원본을 작업 폴더 복사로 대체하지 않는다.
- 새 디자인 클래스 ≠ 새 런타임 아키타입: 덱 전용 클래스는 자유롭게 만들고, `data-archetype`은 검사기가 아는 계열 이름(41계열)만 쓰거나 아예 생략한다(생략하면 엔진이 자동 배정. 모르는 이름은 검사 ERROR다).
- 팩 덱과 legacy 배치·CSS의 혼합 금지, 팩 독립성·`resource_pack` 계약은 `resource-packs.md` 5절 그대로다.

## 5. 디자인 선택은 에이전트가 판단한다

- 팩/legacy 경로·테마·arc·표지·허브·장 배치를 **매번 사용자 승인 받지 않는다**. 라우터 추천·카탈로그·후보 비교는 에이전트의 판단을 돕는 도구이며, 근거를 brief·구성안·최종 보고에 남기면 그것으로 충분하다.
- **후보 비교·시안 3종·3안 비교 같은 절차는 선택적 기법이다.** 사용자가 명시적으로 비교나 승인을 요청했을 때, 또는 에이전트 스스로 시각 비교가 필요하다고 판단할 때 실행한다. 요구가 불명확하면 한 번 묻는 것은 언제나 가능하다(요청 정리 단계 규칙과 같다).
- 선택 기록: 스스로 정했으면 근거 한 줄, 사용자가 정했으면 그 사실을 brief·보고에 남긴다.

## 6. 검사와 품질은 다르다

- `check_deck.py`는 **실행 계약·기술 문제**의 검증 도구다. 깨짐·접근성·계약·외부 자원·대비 같은 안전 가드(ERROR)는 통과해야 하고, 완화하지 않는다.
- 통과 = 디자인 품질 보장이 **아니다**. 취향 규칙(기본 INFO, `--style`에서 WARN)은 어림 표시일 뿐 — 취향 경고만으로 좋은 디자인을 포기하지 않는다.
- 시각 위계·가독성·메시지 전달·도식과 내용의 관계·반복의 적절성·활동과 목표의 연결은 **실제 렌더를 직접 보고 판단한다**(캡처·축소판 육안 — solo 6단계·series 4단계 기준).
- **검사기를 만족시키기 위한 무의미한 도식·클래스·아키타입 이름표 추가 금지.** 도식은 내용을 설명할 때, 클래스는 표현에 필요할 때만 넣는다.
- 생성 성공·정적 검사 통과·렌더 검사 통과·교육 내용 검토는 서로 다른 증거다. 못 한 검사는 NOT_RUN과 이유를 남긴다.
- 완성 덱의 심미 품질은 `design-critique.md`의 독립 크리틱 절차로 확인한다 — 취향이 아니라 목적·메시지 전달 부적합만 평가하고, 구현·미적 선택은 저작 에이전트 자율로 둔다.

## 7. 실패한 장은 부분적으로 회복한다

- 같은 장의 같은 고침이 3회 반복되면, 반복 전에 **원인 분석**부터 한다: 재료가 내용에 안 맞는지, 표현이 넘치는지, 계약을 잘못 썼는지.
- 회복 방법은 내용에 맞게 고른다: 수정 · 단순화 · 검증된 재료(카탈로그 조각·템플릿)로 교체. 카탈로그 사용은 실패 폴백이 아니라 정상 재료다(3절).
- **실패 횟수만으로 덱 전체를 고정 템플릿으로 전환하지 않는다.** 가이드 모드 전환은 `edu-deck/SKILL.md` "자유 모드와 가이드 모드"의 경로를 따르고, 전환 여부는 실패 횟수가 아니라 원인(저작 방식 자체가 안 맞는지, 그 장만 어려운지)으로 판단한다.
