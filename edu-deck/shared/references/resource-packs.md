> **로드 시점**: 경로 결정(`edu-deck/SKILL.md`)에서 팩으로 정해진 새 덱·새 편을 만들 때. 기존 덱은 deck.json에 resource_pack이 있는 경우에만 이 경로로 편집한다. 후보 계산은 `scripts/pack_router.py`다.

# 독립 리소스팩: 디자인과 학습 흐름을 따로 고르기

16팩은 디자인 8종과 학습 흐름 8종이다. 16개의 완성 강의나 검증된 교육 내용이 아니다. 디자인은 정보를 놓는 방식, 흐름은 학습자가 생각하고 행동하는 순서다. 색만 바꾸거나 같은 표지→배경→방법 순서를 반복하지 않는다.

## 1. 새 경로와 기존 경로

| 입력 상태 | 저작 경로 |
|---|---|
| 새 덱 / 새 시리즈 편 | 경로 결정(`edu-deck/SKILL.md`)으로 팩/legacy 를 정한다. 팩으로 정해지면 `pack_router.py` 로 후보 3종·추천·흐름을 계산하고 `resource_pack` 을 명시한다. 기본값은 없고, 애매하면 사용자에게 한 번 묻는다 |
| 기존 `deck.json`에 `resource_pack` 있음 | 선택한 팩과 학습 의도를 유지하며 편집한다 |
| 기존 `deck.json`에 `resource_pack` 없음 | legacy 경로를 유지한다. `composition.md`의 legacy 절과 기존 snippets를 사용한다 |

기존 결과물을 일괄 변환하지 않는다. 기존 덱을 팩으로 바꾸라는 요청이 있으면 내용·배치 재저작과 재검사를 별도 범위로 잡는다. `resource_pack`을 지워 검사를 피하거나 기존 CSS를 새 팩에 섞지 않는다.

새 경로의 파일은 `shared/assets/packs/` 안의 `catalog.json`, `flows.json`, `base.css`, 각 디자인의 `style.css`·`template.html`이다. 실제 ID·콘텐츠 예산은 catalog, 단계 문안은 flows를 기준으로 읽는다. 이 문서의 선택표는 판단을 돕는 설명이다.

## 2. 선택 계약: 하나의 디자인, 하나의 주흐름

```json
{
  "title": "업무 오류를 진단하는 연습",
  "output": "diagnosis.html",
  "resource_pack": {
    "design": "casebook",
    "flow": "diagnose",
    "activities": ["compare", "discussion"]
  }
}
```

- `design`: 8개 디자인 ID 중 정확히 하나. 한 덱 안에서 디자인을 무작위로 바꾸지 않는다.
- `flow`: 8개 흐름 ID 중 정확히 하나. 전체 학습 순서는 이 흐름으로 설명할 수 있어야 한다.
- `activities`: 생략하거나 빈 배열. 필요하면 **주흐름과 다른 ID를 중복 없이 최대 2개** 쓴다. 보조 흐름 전체를 이어 붙이지 말고 필요한 활동만 주흐름 단계에 삽입한다.
- `resource_pack` 안에는 `design`, `flow`, `activities`만 허용한다. `comment` 등 알 수 없는 키는 출력 전 오류로 거부한다. 선정 설명은 이 객체에 추가하지 않고 `brief.md`에 쓴다.
- 선정 이유를 `brief.md`에 쓴다: 청중의 사전 지식 → 교육 뒤 수행 행동 → 확인할 증거 → 주흐름 → 자료를 잘 보여 주는 디자인. 보조활동은 어느 단계의 어떤 부족함을 보완하는지 적는다.
- 추천 조합은 시작점이지 강제 대응표가 아니다. 예를 들어 현장형(field)도 따라하기가 아니라 오류 진단을 가르칠 수 있다. 교육 목적이 달라지면 같은 디자인에서도 흐름을 달리 고른다.

### 디자인 선택표

| 디자인 | 고르는 이유 | 다른 디자인이 나은 때 |
|---|---|---|
| 편집 잡지형 `editorial` | 개념과 근거를 읽고 연결한다. 큰 질문과 본문 열, 곁의 근거·읽기 경로 도식을 사용한다 | 조작 절차가 중심이면 field/workbook |
| 실험 노트형 `lab` | 관찰·검증·수정 기록을 가까이 놓는다 | 토론 자체가 핵심이면 seminar |
| 현장 매뉴얼형 `field` | 순서와 점검 항목을 빠르게 찾아야 한다 | 결말을 숨긴 사례 판단이면 casebook |
| 사례 기록형 `casebook` | 상황 설명과 증거를 구분해 판단한다 | 공간적 관계가 핵심이면 atlas |
| 지도·도해형 `atlas` | 개념의 관계·위치·연결을 보여 준다 | 수치 비교는 briefing. 장식 연결선을 수량 그래프로 해석하지 않는다 |
| 워크북형 `workbook` | 읽는 면과 직접 해보는 면을 오가며 기록한다 | 짧은 전체 발표는 editorial/briefing. 종이 응답 영역은 저장되는 입력창이 아니다 |
| 데이터 브리핑형 `briefing` | 핵심 주장·근거·행동을 정렬해 판단한다 | 근거가 부족하면 숫자나 차트를 만들어 채우지 말고 조사부터 한다 |
| 세미나형 `seminar` | 큰 질문과 여백을 두고 생각·경청·대화를 이끈다 | 복잡한 절차를 한 화면에 담아야 하면 field |

### 학습 흐름 선택표

전체 단계와 단계별 `prompt/body/evidence/action`은 `assets/packs/flows.json`에 있다. 각 흐름의 `outcome`은 학습 성과, `assessment`는 성과를 판단할 실제 산출물이다.

| 주흐름 | 학습자가 해낼 일 | 단계의 핵심 순서 | 평가 증거 |
|---|---|---|---|
| 문제 해결 `problem` | 업무 문제의 해법을 시험하고 다른 상황에 적용 | 불편 관찰 → 성공 기준 → 대안 → 작은 시험 → 전이 | 문제 정의·전후 결과·새 상황 판단 |
| 사례 판단 `case` | 불완전한 정보에서 판단하고 수정 | 첫 선택 → 사실/추정 → 추가 단서 → 결과 회고 → 경계 사례 | 초기/수정 판단과 결정적 근거 |
| 따라하기 `follow` | 절차를 수행하고 실패에서 복구 | 준비 → 전체 시연 → 단계 실습 → 복구 → 독립 수행 | 실제 출력·복구 기록·혼자 만든 결과 |
| 탐구 `inquiry` | 예측을 관찰과 대조하며 원리 설명 | 현상 → 사전 예측 → 조작 → 설명 수정 → 새 조건 예측 | 예측/관찰 기록과 적용 한계 |
| 비교 선택 `compare` | 같은 기준으로 구별하고 상황별 선택 | 기준 → 동일 조건 비교 → 상충 판단 → 조건 변경 | 비교 근거·포기한 이점·조건부 선택 |
| 오류 진단 `diagnose` | 증상에서 원인을 가르고 복구 확인 | 증상/경계 → 후보 → 판별 검사 → 최소 복구 → 재확인 | 원인 판별·수정·재시험 기록 |
| 토론 `discussion` | 근거를 들어 논의하고 입장 수정 | 쟁점 → 개인 생각 → 상대 재진술 → 반례 → 합의/이견 | 초기/수정 입장·상대 요약·미해결 질문 |
| 프로젝트 `project` | 사용 가능한 결과물을 만들고 개선 | 사용자/기준 → 계획 → 초안 → 사용 관찰 → 수정 → 인계 | 결과물·사용 기록·수정 근거·인계 |

정답을 외워 고르는 퀴즈만으로 실습·토론·프로젝트의 완료를 판정하지 않는다. 확인 문제는 개념 확인에 쓰고, 최종 성과는 위 표의 실제 행동·산출물로 확인한다. 토론은 특정 의견에 동의했는지가 아니라 근거를 검토하고 상대 관점을 이해했는지를 본다.

## 3. 생성: 저작용 뼈대에서 시작하기

`<base>`는 설치된 `edu-deck/shared`의 실제 경로다. `init` 출력은 비어 있거나 아직 없는 폴더여야 한다. brief/research를 이미 만든 폴더에 실행하지 않는다. 별도의 빈 `scaffold/`에서 생성한 후 `deck.json`과 `src/`를 기존 파일을 덮어쓰지 않도록 옮긴다. 새 작업 폴더라면 먼저 init하고 그 폴더에 brief/research를 작성해도 된다.

```bash
python3 <base>/scripts/resource_packs.py init <빈-덱-폴더> --design casebook --flow diagnose --title "업무 오류 진단"
```

명령은 주흐름의 각 단계에 대응하는 `src/NN-<flow>.html`과 `deck.json`을 만든다. `activities`를 자동 삽입하지 않는다. 필요한 보조활동은 outline에 위치와 증거를 설계한 뒤 직접 저작한다. `outcome`·`assessment` 메타데이터도 자동으로 평가 문항이 되지 않는다.

**생성 직후는 검증된 교육 자료가 아니다.** 단계 문안과 자동 노트는 저작 안내다. 자리표시 탐지가 0이어도 교육 내용을 완성했다는 뜻이 아니다. 공개 자료·사용자 제공 자료를 조사한 뒤 화면 문구, 사례, 근거와 노트를 모두 주제에 맞게 다시 쓴다.

템플릿 치환 토큰은 `{{TITLE}}`, `{{KICKER}}`, `{{PROMPT}}`, `{{BODY}}`, `{{EVIDENCE}}`, `{{ACTION}}` 여섯 개다. 생성기는 모두 **HTML 이스케이프된 일반 문자열**로 넣는다. 토큰 값에 HTML/SVG/스크립트를 넣어 구조를 만드는 방식이 아니다. 도해나 표가 필요하면 생성된 `src/*.html`을 직접 편집한다. `«…»` 같은 자리표시도 최종본에 남기지 않는다.

새 독립 생성 경로는 `resource_packs.py init` → 직접 저작한 `src/` → `build_deck.py`다. `dev/port.py`나 `make_snippets.py`를 호출하지 않으며, 배포된 팩 파일·공통 실행 자산만으로 다시 생성한다. 원래의 `Downloads` 교육 HTML은 필요하지 않다. 이 말은 교육 내용의 조사까지 오프라인으로 대체한다는 뜻은 아니다. legacy 포팅 도구는 새 팩의 생성·재생성 절차에 넣지 않는다.

## 4. 단계와 슬라이드는 같은 단위가 아니다

단계 하나는 목적이 같은 여러 슬라이드가 될 수 있다. 생성된 반복 템플릿을 장수만 늘려 그대로 발행하지 않는다. 선택한 디자인의 글꼴·여백·선·색 체계를 유지하면서 **자료와 행동에 맞는 변형**을 직접 만든다.

- 읽기: 주장과 근거의 대비, 실제 자료의 부분 확대.
- 비교: 동일 기준의 양쪽 표, 차이가 드러나는 전후 자료.
- 절차: 수행 순서, 정상 상태와 실패 상태의 짝.
- 탐구: 예측을 먼저 보여 주고 관찰 결과를 단계 공개; 가정과 한계 별도 표기.
- 활동: 질문과 응답 공간, 동료 검토 항목, 결과물 평가표.
- 정리: 처음 질문에 대한 수정 답과 다음 적용 조건.

덱마다 여러 종류의 변형을 배치하고 축소판에서 반복을 확인한다. 같은 구성 4장 연속은 재검토한다. 동일 기준으로 비교하는 실습 기록처럼 반복이 필요한 경우에는 이유를 outline에 남긴다. 표지·순서는 필요에 맞게 합치거나 짧게 하고, 오프닝을 항상 cover→why→how로 강제하지 않는다. 출처 목록은 항상 찾을 수 있게 두고 마지막에는 학습 성과나 다음 행동을 확인한다.

### 팩 덱의 outline 양식

```markdown
# 구성안: 업무 오류 진단
- 청중/시간/선행 지식: …
- 학습 성과와 완료 증거: …
- resource_pack: design=casebook, flow=diagnose, activities=[compare]
- 선택 이유: 사건 기록과 원인 판별을 함께 읽는다. 후보 비교 활동은 판별 검사 단계에 넣는다.
- 자료 공백/가정/안전 경계: …

| No | 흐름 단계 | 디자인 안의 배치 변형 | 질문/핵심 메시지 | 학습자 행동 | 확인할 증거 | 사실 ID | 노트/복습 열쇠 |
|---|---|---|---|---|---|---|---|
| 01 | 증상/경계 | 상황 기록+관찰 비교 | 관찰과 추정을 어떻게 나누나요? | 증상만 적기 | 증상 기록 | 조사 후 연결 | symptom |
| 02 | 원인 후보 | 후보별 예상 비교 | 어떤 결과가 후보를 가르나요? | 판별 질문 만들기 | 후보/검사표 | 조사 후 연결 | cause |
```

전체 수업 시간은 설명뿐 아니라 실습·토론·피드백 시간을 포함해 배분한다. 단계 수를 권장 장수로 착각하지 않는다. 짧게 만들 때도 해당 흐름의 성과 확인은 남긴다.

## 5. 실행 기능과 표현 계약

팩 덱은 기존 교육 실행 기능을 재사용하지만 legacy 배치 클래스에 의존하지 않는다.

- 장 루트는 `section.slide.pack.pack-<design>`과 `data-design="<design>"`, 내용에 맞는 `data-archetype`입니다. 새 템플릿에는 기본 이름이 있고 기존 이름 없는 팩은 공통 엔진이 연결합니다. 단계 공개는 기존 `data-step`, 노트는 `aside.notes`, 복습 대상은 `data-key` 계약을 유지한다. 선택한 팩의 루트 클래스는 각 장에서 유지한다.
- 새 배치는 `pack-*` 또는 해당 디자인 전용 클래스와 작업 폴더 `src/*.css`로 만든다. `.cx-*`, `.win`, `.card`, `.title`, `.callout`, `.rules-dark` 등 legacy 배치 클래스와 `assets/css/`·`assets/snippets/`를 팩 덱의 스타일 재료로 넣지 않는다. **아이콘 묶음(icons.svg·`icons.md`의 `i-*`·`ah*` 화살촉)과 개념 SVG 도식(`diagrams.md` 문법)은 예외로 팩 덱에서도 쓸 수 있다.** `.slide`, `.notes`, `.fact`, `.chk`와 공개 동작 속성은 **기능 계약 예외**다.
- 시리즈에서도 사용할 사용자 `src/*.css`는 편 내부 클래스 선택자(예: `.lesson-panel`)를 사용한다. 사용자 변수도 `.pack-editorial` 같은 편 내부 클래스에 선언한다. `:root`, `html`, `body`, 루트 ID 및 편 밖 조상에 의존하는 선택자는 지원 계약에 포함하지 않는다. 조립기는 제공 자산의 정확한 `:root{` 토큰을 편의 `:scope`로 바꾸지만, 사용자 CSS의 `:root {` 등 임의 문법까지 변환하지 않는다.
- 공통 `.ed-diagram`·흐름·계층·관계·비교·지도·장면 어휘는 `classes.md`를 따릅니다. 이는 legacy 배치 혼합이 아니라 두 경로의 공통 설명 자산입니다. 개념 SVG 도식의 장별 문법(k-* 도형·글자 클래스·ah-* 화살촉)은 `diagrams.md`를 따릅니다. 색·Pretendard·모티프·단계 시그니처는 `DESIGN_TOKENS.md`·`MOTION_LIBRARY.md`를 따릅니다.
- 비유·예시는 직접 작성한 인라인 SVG/도식/장면과 짝짓습니다(문법은 `diagrams.md`). 필요한 라스터는 합계 1.5MB 이내 base64로 넣습니다. 외부 로딩·조각 스크립트·CSS 애니메이션·SMIL은 금지합니다. UI·키보드·모션 엔진을 조각에서 재구현하지 않습니다.
- 숫자·날짜·조항은 기존 조사 계약을 따른다: `.fact[data-src]` 칩과 `data-archetype="sources"` 출처 장의 `[data-src]` 항목을 연결한다. 출처 장의 모양은 선택한 팩으로 직접 작성한다. 내용 검증 절차는 `research.md`를 읽는다.
- 모든 장의 자동 노트를 **조사된 실제 발표자 노트 110~450자**로 교체한다. 설명, 활동 진행, 예상 답/오해와 피드백, 보충 근거·날짜(해당할 때), 다음 연결을 쓴다. `composition.md` 6절 참고. 주제 없는 진행 문구를 늘려 글자 수만 맞추지 않는다.
- `summary`·`glossary`는 `composition.md` 8절대로 작성한다. 팩 덱은 legacy 마무리 장의 클래스 추출에 의존하지 않도록 명시 데이터 작성을 권장한다.

### 확인 문제: 호환 마크업만, 모양은 선택한 팩

`data-archetype="check"`를 장에 붙이고 아래 구조를 선택한 팩의 질문 영역에 놓는다. 질문·해설은 실제 주제와 조사 결과로 교체한다. 정답 하나, 보기 둘 이상이며 해당 장 또는 같은 편 안에 복습 대상 `data-key="concept"`가 있어야 한다.

```html
<div class="chk" data-review="concept">
  <p class="chk-q"><span class="chk-n">1</span>관찰한 사실에 해당하는 것은 무엇인가요?</p>
  <div class="chk-opts">
    <button class="chk-o" data-ok>직접 기록한 결과입니다</button>
    <button class="chk-o">아직 확인하지 않은 원인입니다</button>
  </div>
  <p class="chk-why">관찰은 확인한 결과이고, 원인 추정은 추가 검사가 필요합니다.</p>
</div>
```

`chk-fb`, `chk-go`, `chk-again`은 실행 엔진이 만든다. 직접 생성하지 않는다. 기존 퀴즈·단계 공개·자습·인쇄·용어집·시리즈 진도를 보존한다. 크레파스 저작 속성은 공통 모션 엔진의 캔버스 크레파스 표시로 연결하며 팩 덱이 별도 캔버스·스크립트 루프를 추가하지 않는다. 팩 덱의 확인 문제는 `.chk` 계약을 우선 사용하고 legacy quiz-ab의 시각 배치 자체를 가져오지 않는다. 크레파스 `data-crayon` 속성은 `classes.md`의 기능 설명대로 사용하며 자동 채점 표시를 수동으로 중복하지 않는다.

## 6. 검사와 완료 판단

1. **선택**: 유효한 디자인·주흐름 하나, 서로 다른 보조 흐름 최대 2개. brief의 선택 이유와 outline이 일치한다.
2. **교육 내용**: 저작 안내 문구·자동 노트를 실제 내용으로 교체했다. 흐름의 결과물로 성과를 확인한다. 사실은 조사 기록과 연결되어 있다.
3. **배치 다양성**: 같은 디자인 안에서 질문·자료·활동에 맞는 변형을 썼다. 반복 템플릿만 이어 붙인 덱이 아니다.
4. **기능·화면**: solo의 build_deck/check_deck/verify_sources를 실행하고 모든 장·단계·확인 문제·크레파스·자습·인쇄·용어집을 확인한다. 시리즈는 각 편 검사 후 build_series/check_series와 편 전환·진도·같은 편 복습을 확인한다.
5. **독립성**: 팩 덱은 선택한 팩의 자산 경로를 사용한다. legacy 배치 클래스·snippets·CSS를 팩 덱에 넣거나 원본 Downloads를 재생성 의존성으로 삼지 않는다(아이콘 묶음·개념 SVG 도식은 허용).

시리즈는 legacy 편만 있어도 CSS 격리에 native `@scope` 지원이 필요하다. 현재 렌더·동작 검증은 Chrome에서만 수행했으며, 다른 브라우저·버전과 지원 최저 버전은 미검증이다. 단일 HTML·외부 의존성 없음은 모든 브라우저 호환을 뜻하지 않는다. 배포 대상 브라우저에서 따로 확인한다.

생성 성공, 정적 검사 통과, 브라우저 검사 통과, 실제 교육 내용 검토는 서로 다른 증거다. 하지 못한 검사는 NOT_RUN과 이유를 남긴다. 샘플 뼈대의 통과만으로 최종 강의가 완성됐다고 보고하지 않는다.

## 7. 공개 교본에서 참고한 원리와 경계

아래는 공개 페이지에서 확인한 **구성 원리의 참고처**다. 효과의 정량적 우월성을 주장하는 근거가 아니다. CSS·SVG·이미지·문장·전체 배치를 가져오지 않는다. 사이트 단위의 허용 문구를 모든 개별 자산의 이용 허가로 해석하지 않는다.

|---|---|---|
| [Assertion–Evidence](https://www.assertion-evidence.com/) | 메시지 중심의 문장과 시각적 근거 | 주장/질문과 확인할 자료를 연결한다 |

이 카탈로그의 단계·문구·마크업·스타일은 독자적으로 작성한다. 외부 자산을 나중에 추가하려면 파일별 출처·허용 조건을 별도로 확인한다. 현재 팩은 그 자산의 라이선스에 기대어 생성하지 않는다.
