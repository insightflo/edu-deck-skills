> **로드 시점**: 구성안(outline.md)을 짤 때. 새 덱·새 편의 기본은 legacy 아키타입 경로(아이콘·조각·개념 SVG 도식)이므로 이 문서의 공통 규칙과 5절 아키타입을 읽는다. 사용자가 리소스팩을 요청하거나 시안을 보고 골라 팩 경로로 가기로 했을 때만 `resource-packs.md`를 먼저 읽는다.

# 내용 구성: 주제 → 파트 → 슬라이드

## 0. 경로를 먼저 고른다

- **새 덱과 새 시리즈 편**: 기본은 legacy 아키타입 경로다(아이콘·조각·개념 SVG 도식, 아래 1~5절·7절). 사용자가 리소스팩을 요청하거나 시안을 보고 골라 팩 경로로 가기로 했을 때만 `deck.json.resource_pack`에 디자인 1종·주흐름 1종을 명시하고, 필요하면 다른 흐름의 보조활동을 최대 2종 고른다. 이때 흐름 단계·성과·평가 증거는 `assets/packs/flows.json`을 기준으로 구성하고 outline 양식과 배치 변형 지침도 `resource-packs.md`를 따른다.
- **기존 resource_pack 덱**: 선택한 흐름에 맞춰 편집한다. 아래 legacy 줄거리에 맞추려고 재배열하지 않는다.
- **기존 resource_pack 없는 덱**: 아래 1~5절·7절의 legacy 규칙을 유지한다. 원본 덱의 문장·사례는 옮기지 않는다.
- **공통 규칙**: 한 장 한 메시지, 실제 업무에 맞는 예시, 처음 나오는 용어 풀이, 조사한 사실과 출처 연결, 6절 발표자 노트, 8절 자습 데이터. 비유·예시에는 도식·일러스트·장면 모형을 하나 이상 짝지으며 텍스트 전용 본문은 statement·퀴즈 질문 정도로 제한한다. 모든 장은 [MOTION_LIBRARY.md](MOTION_LIBRARY.md)의 의미별 임팩트와 정적 대체를 갖는다. legacy 클래스·고정 파트 순서·장수 비율은 공통 규칙이 아니다.

팩 경로를 택한 덱은 `problem/case/follow/inquiry/compare/diagnose/discussion/project` 중 학습자가 끝에 해낼 행동에 맞는 흐름을 고른다. 시간에는 설명뿐 아니라 수행·토론·피드백을 포함한다. 주흐름의 성과를 확인하는 활동을 남기고, 같은 디자인 안에서도 비교·관찰·시연·활동·정리의 배치를 달리한다. 초기 생성물은 뼈대일 뿐이므로 실제 조사 내용과 110~450자 노트로 교체한 뒤 검사한다.

아래 legacy 부분은 참고 덱(45장 사내 교육)에서 다듬은 구성 규칙이다. 새 덱·새 편의 기본값으로 사용한다. 리소스팩을 요청·선택한 덱만 `resource-packs.md`의 양식으로 바꾼다.

## 1. Legacy 기본 줄거리 (덱의 기본 경로. `resource_pack` 지정 덱은 `resource-packs.md`)

청중이 "그게 뭔데?" → "우리랑 무슨 상관?" → "어떻게 해?" → "실제로는?" → "뭘 조심해?" → "그래서 이번 주에 뭘 해?" 순서로 묻는다고 보고, 그 순서대로 답한다.

| 순서 | 블록 | 하는 일 | 대표 아키타입 (나오는 순서) |
|---|---|---|---|
| 0 | 표지 | 교육 이름, 제목, 핵심어 3~4개, 부제, 날짜 | cover |
| 0 | 순서 | 파트 3~5개를 학습자 질문으로. 정리 문장 = 내려가는 길("큰 그림 → 우리 상황 → 방법 → 확인") | agenda |
| ① | 큰 그림 | 왜 지금 → 한 장 구조도(구성 요소에 ①②③④) → 요소별 확대 → 정리: 사례 하나를 구조 전체에 통과시키기 | timeline → map → 요소마다 mechanism·traits-grid·meter·compare-2·hub·levels·tile-grid → sequence |
| ② | 우리 상황 | ①의 번호 그대로 우리 제도·도구·현장에 대응 → 할 수 있는 것 → 방식 둘 → 화면·절차 둘러보기 → 선택지 → 상시 규칙 | mapping → tile-grid → compare-2 → mock-legend → mock-options → compare-2(choose) → frame-form(rules) |
| ③ | 잘하는 법 | 파트를 여는 핵심 문장(주황 전면) → 하나씩 더하며 결과가 좋아지는 시연 → 작업 틀 → 주제별 요령 2~4개 → 전후 비교 → 퀴즈 | statement → build-up → frame-form → worked-example(tips) → before-after → quiz-ab |
| ④ | 현장 적용 | 쓰는 곳 묶음 → 분류 퀴즈 → 실제 업무 예시 여러 장(입력 + 결과 모형 + 포인트) | tile-grid → quiz-sort → worked-example × 3~6 |
| ⑤ | 위험·확인 | 실패 유형 → O/X 퀴즈 → 확인 방법 → 교차 확인 → 꼭 지킬 3가지(어두운 배경) | mock-legend(cases)·compare-2 → quiz-ox → worked-example → before-after(cross-check) → rules-dark |
| 끝 | 실천·마무리 | 이번 주 할 일 3~4개(누르면 체크) → 참고 자료 → 행동 한 문장 + 요약 알약 3개 + 질문 받기 | checklist → sources → closing |

- 참고 자료(sources)는 마무리 바로 앞에 둔다. 덱이 행동 촉구로 끝나게 하려는 것이다. 출처 칩(.fact)이 하나라도 있으면 반드시 넣는다.
- 파트 이름과 개수는 주제에 맞게 바꾼다(3~5개). 2절 유형표를 따른다.

## 2. Legacy 주제 유형별 파트 짜기

주제가 어느 유형인지 먼저 정한다. 섞여 있으면 교육 뒤 청중이 해야 할 행동에 가까운 쪽을 고른다. 운영 매뉴얼·기술이전 교육처럼 절차를 익혀서 반복하는 것이 핵심이면 (a)와 (c)를 섞되 sequence·checklist·worked-example 중심으로 잡는다.

### (a) 도구·시스템 도입 — 예: 새 전자결재 시스템, 메신저 전환
| 파트 | 학습자 질문 | 담는 것 | 아키타입 |
|---|---|---|---|
| ① | 왜 바꾸나? | 지금 방식의 불편 → 바뀌는 흐름, 시스템 구성 한 장 | timeline, map, compare-2(flow) |
| ② | 내 화면에는 뭐가 있나? | 메뉴 둘러보기, 할 수 있는 일, 권한·결재선 | mock-legend(tour), tile-grid, mock-options |
| ③ | 어떻게 처리하나? | 핵심 업무 1~2개 단계 시연, 입력 틀 | statement, build-up, frame-form(form) |
| ④ | 내 업무에서는? | 부서별 대표 업무 3~5개(양식 화면 + 포인트) | worked-example(form-points, doc-points) |
| ⑤ | 실수하면? | 자주 하는 실수, 되돌리기, 문의처 | before-after, quiz-ox, rules-dark |

### (b) 법규·안전·컴플라이언스 — 예: 폭염 작업 안전, 개인정보 유출 대응
| 파트 | 학습자 질문 | 담는 것 | 아키타입 |
|---|---|---|---|
| ① | 무엇이 위험하고 왜 지금인가? | 사고·위반 추이(공식 통계), 위험이 생기는 구조 | timeline, map, levels, meter |
| ② | 우리에게 적용되는 규정은? | 조항·대상·시행일, 우리 현장에 대입, 판단 기준 | mapping, compare-table, levels, frame-form(rules) |
| ③ | 어떻게 지키나? | 핵심 행동 문장, 절차 단계, 점검 틀 | statement, sequence, frame-form(form), build-up |
| ④ | 현장에서는? | 상황별 사례: 점검표·업무 일지·단체방 공지 모형 | tile-grid, quiz-sort, worked-example(doc/sheet/msgr-points) |
| ⑤ | 어기거나 놓치면? | 위반 결과(벌칙 조항), 흔한 착각 O/X, 꼭 지킬 3가지 | compare-2, quiz-ox, rules-dark |

### (c) 업무 방법·스킬 — 예: 보고서 작성법, 회의 진행법
| 파트 | 학습자 질문 | 담는 것 | 아키타입 |
|---|---|---|---|
| ① | 좋은 결과물은 무엇이 다른가? | 나쁜 예/좋은 예 대비, 구성 요소 지도 | before-after, map, traits-grid |
| ② | 우리 업무에서는 언제 쓰나? | 문서 종류·상황별 대응, 우리 양식 | mapping, tile-grid, compare-table |
| ③ | 어떻게 하나? | 핵심 비유 문장, 하나씩 고쳐 가는 시연, 작성 틀 | statement, build-up, frame-form, worked-example(tips) |
| ④ | 실제로 해 보면? | 실제 문서·메일 고치기 예시 3~6장 | worked-example(doc/mail-points), before-after |
| ⑤ | 자주 틀리는 곳은? | 흔한 실수, 스스로 점검, 지킬 3가지 | quiz-ox, frame-form(rules), rules-dark |

### (d) 개념·리터러시 — 예: 재무제표 읽기, 통계 숫자 읽는 법
| 파트 | 학습자 질문 | 담는 것 | 아키타입 |
|---|---|---|---|
| ① | 이게 무엇인가? | 등장 배경, 구성 요소 지도, 요소별 정의(용어 + 비유) | timeline, map, traits-grid, hub, mechanism |
| ② | 어디서 마주치나? | 우리 업무·생활에서 보이는 곳 | mapping, tile-grid |
| ③ | 어떻게 읽나? | 읽는 순서, 핵심 질문 틀, 비교 | statement, sequence, frame-form, compare-table |
| ④ | 실제 자료로 읽어 보면? | 실제 모양의 자료(가상 값) 읽기 | worked-example(sheet/doc-points), quiz-sort |
| ⑤ | 오해하기 쉬운 것은? | 흔한 오해 O/X, 확인 습관 | quiz-ox, before-after, rules-dark |

## 3. Legacy 분량과 비율

- 1장 ≈ 1분이 기준이다(참고 덱 45장 ≈ 45~60분). 시간을 모르면 45분, 32~40장으로 잡는다.
- 파트 비율(참고 덱): ① 27% · ② 16% · ③ 20% · ④ 18% · ⑤ 11% · 표지·순서·실천·마무리 8%.

| 시간 | 장 수 | 줄이는 법 |
|---|---|---|
| 15분 | 12~15 | ① timeline·map·sequence, ② mapping 1장, ③ statement + build-up 또는 frame-form + 퀴즈 1개, ④ 예시 1~2장, ⑤ rules-dark |
| 30분 | 22~28 | ① 요소별 확대를 요소당 1장, ② 3~4장, ③ 5~6장, ④ 예시 3장, ⑤ 3장 |
| 45분 | 32~40 | 1절 줄거리 전체, 예시 4~5장 |
| 60분 | 42~50 | 예시 6장, 요소별 확대 2장씩 |

짧은 덱에서도 빼지 않는 것: 표지, 순서, 파트를 여는 statement 1장, 퀴즈(15장 이상이면 1개 이상, 30장 이상이면 3개. 자리는 1절 줄거리대로 ③ 끝 · ④ 쓰는 곳 묶음(tile-grid) 뒤 · ⑤ 실패 유형 뒤), 확인 문제 check(파트가 끝날 때마다 1장, 한 장에 문제 1~2개. 꼭 짚고 넘어갈 개념이 헷갈리기 쉬운 것만), 위험·확인(최소 rules-dark), checklist, closing, 출처 칩이 있으면 sources.

## 4. Legacy 슬라이드 한 장의 규칙

내용 원칙은 0절의 공통 규칙대로 유지하되 아래 클래스·파트 번호·단계 배치는 legacy용이다. 새 팩의 클래스·변형·공개 순서는 `resource-packs.md`를 따른다.

- **한 장 한 메시지.** 장은 나눠진 칸이 아니라 설명의 한 단위다 — 지배적 생각이 하나다. 제목 = 그 메시지를 담은 한 줄. `expression.md` 1절의 제목 유형 중 하나로 쓴다: 주장형·조언형·질문형·비교형은 존댓말 문장, 정의형은 "용어: 일상 비유", 예시 장은 예시형 "…하기". "개요", "현황" 같은 이름표 제목은 쓰지 않는다.
- **비교는 같은 속성을 같은 순서로 나란히 둔다.** compare-2 의 좌우와 compare-table 의 행은 같은 속성 순서를 지킨다 — 청중이 기억에 의지하지 않고 눈으로 비교한다.
- **눈썹(eyebrow) = 위치 표시.** `N. 파트 이름`, 필요하면 ` · ② 요소` 또는 ` · 예시 2`를 붙인다. 퀴즈는 눈썹 대신 파란 `퀴즈 N` 꼬리표. 확인 문제는 눈썹에 `확인 문제 N / M`.
- **정리 문장(callout)** = 이 장에서 가져갈 한 줄. 어두운 띠에 앞부분 `<b>` 강조. 마지막 단계에 보인다. 모든 장에 넣지 않는다(참고 덱은 45장 중 14장). 요소 설명·비교·전후 비교의 끝에 쓴다.
- **번호 이어 쓰기.** ①의 구조도 번호(①②③④)를 요소별 슬라이드 눈썹, ②의 mapping, ①의 정리 sequence 에 그대로 쓴다. 청중이 지금 지도 어디쯤인지 안다.
- **나선 반복.** ③에서 만든 틀(예: "물·그늘·휴식", "결론·근거·요청")을 ④ 예시의 포인트, checklist, closing 알약에서 다시 부른다.
- **예시는 청중의 실제 업무물.** 공문·점검표·업무 일지·엑셀·신청 화면·단체방 문자. 이름·숫자는 그럴듯한 가상 값으로 쓰고 실제 개인정보는 쓰지 않는다.
- **용어는 처음 나올 때 풀이.** `용어 <span class="en">English</span>` + 일상 비유 한 줄(예: "현금흐름표는 회사의 통장 입출금 내역입니다").
- **숫자에는 출처 칩.** research.md 의 원문대조·두출처일치 사실만 화면에 쓴다. 확인 못 한 숫자는 화면에 쓰지 않는다.
- **단계 등장.** 읽는 순서대로 하나씩, 정리 문장은 마지막. cover·statement·closing 은 단계 없음. 보통 2~5단계, 많아도 7단계.
- **같은 아키타입은 3장까지 연속**(worked-example 예시 묶음은 예외).

## 5. Legacy 내용 → 아키타입 고르기

| 보여 줄 내용 | 아키타입 (변형) |
|---|---|
| 파트 순서를 질문으로 | agenda |
| 시간에 따른 변화·연혁·개정 이력 | timeline |
| 전체 구조 한 장, 구성 요소에 번호 | map |
| 입력 → 처리 → 결과 후보(원리) | mechanism |
| 성질·특징 2~4개 | traits-grid |
| 정해진 한도를 나눠 쓰는 것(시간·예산·용량·구성비) | meter |
| 두 방식·두 흐름 비교 | compare-2 (flow 흐름 도식 · diagram 연결 도식 · list 목록) |
| 둘 중 언제 무엇을 고르나 | compare-2 (choose) |
| 항목별 A/B 비교 3~5행 | compare-table |
| 중심 하나 + 둘레 요소 | hub |
| 수준·등급이 올라가는 구조 | levels |
| 기능·사례·도구 묶음 6~8개 | tile-grid (cards 3×2 · features 4×2 · icons 3×2) |
| 사람·부서·시스템 사이 주고받는 순서 | sequence |
| 앞의 구조를 우리 것에 대응 | mapping |
| 실제 화면 둘러보기(번호 ↔ 설명) | mock-legend (tour) |
| 실패·사례 몇 개를 화면 위에 표시 | mock-legend (cases) |
| 화면 + 선택지(모드·방식) | mock-options |
| 파트를 여는 핵심 한 문장 | statement (orange · 위험 파트는 dark) |

### Legacy 단계 등장 리듬 (장 배치 가이드)

단계 등장이 지루하지 않게 장 배치로 리듬을 만든다. 각 유형의 강한 순간은 공통 셸이 담당한다. 조각이 정적이라는 규칙은 셸 모션을 금지하지 않는다. 어느 단계에서 멈춰도 이해할 수 있어야 하며, 모션을 꺼도 현재 단계의 내용이 완결되어야 한다.

| 구간 | 배치 | 근거 |
|---|---|---|
| 오프닝(1~5장) | 표지 → 순서(agenda 단계 등장) → 첫 파트 statement | 진입은 이 세 장으로 끝낸다 |
| 본론(파트별) | 강조형 장(한 장 한 메시지: statement·compare-2·tile-grid·before-after)과 흐름형 장(단계를 밟는: mechanism·sequence·build-up·worked-example)을 대략 7:3 으로 섞는다 | 설명이 많은 덱일수록 강조형으로 쉬게 주고 흐름형으로 몰입시킨다. 같은 아키타입이 3장 이어지면 흐름형 하나 끼워 넣는다(검사의 4장 연속 규칙보다 먼저) |
| 파트 전환 | 파트 첫 장을 statement 변형(orange, 주의·위험 파트는 dark)으로 | "챕터가 바뀌었다"는 신호는 화면 효과가 아니라 전체 장이 한다 |
| 마무리 | 다시 구조로 모은다(한 장 요약·checklist·확인 문제) → closing 한 문장 | 마지막 장에는 새 정보를 넣지 않는다 |

셸의 의미별 시그니처와 팩 모티프는 [MOTION_LIBRARY.md](MOTION_LIBRARY.md)에 정의한다. 조각은 정적 구조만 쓰고 애니메이션을 넣지 않는다.

## 6. 발표자 노트 (두 경로의 모든 슬라이드)

- 110~450자, 말하듯 존댓말. 처음 보는 발표자도 노트만으로 진행할 수 있게 쓴다. 새 팩 생성기의 자동 노트는 저작 안내이므로 조사된 실제 주제 설명으로 반드시 교체한다. 글자 수 통과만으로 내용 완성으로 보지 않는다.
- 담을 것(순서대로): ① 화면 설명 한두 문장 ② 진행 지시("→를 누를 때마다 하나씩 나옵니다", "청중에게 먼저 물어보세요", "손 들어 보게 하세요") ③ 화면에 없는 보충 사실 + 출처·날짜 ④ 시간이 모자랄 때 건너뛸 곳 ⑤ 다음 장으로 잇는 한 문장.
- 퀴즈 노트: 정답과 이유, 틀린 답을 고른 사람에게 할 말.
- 확인 문제(check) 노트: 정답, 해설 요약, 틀린 사람을 위해 "다시 보기"로 돌아가는 장 안내.
- 예시 노트: 실제로 시연하는 방법, 우리 조직 상황이 다르면 바꿔 말할 문장.
- 화면 글을 그대로 읽는 노트는 쓰지 않는다.

## 7. Legacy outline.md 양식

새 덱의 기본 양식이다. `resource_pack`을 지정한 덱만 `resource-packs.md`의 흐름 단계·학습자 행동·평가 증거·배치 변형 양식을 쓴다.

1단계에서 초안(파트와 파트별 조사 질문)을 쓰고, 조사 뒤 3단계에서 표를 채워 확정한다. 슬라이드를 쓰기 전에 이 표가 완성돼 있어야 한다.

```markdown
# 구성안: 폭염 작업 안전
- 청중: 건설 현장 관리감독자 (비전공, 현장 경력 5년 이상)
- 시간: 30분 · 장 수: 26장 · 주제 유형: (b) 법규·안전 · 기준일: 2026-10-30
- 교육 뒤 청중이 할 수 있는 것: ① 체감온도 단계별 조치를 말한다 ② 휴식 의무 대상을 판단한다 ③ 온열질환 의심 때 바로 할 일을 안다
- 가정: 사내 폭염 규정 정보 없음 → "우리 현장" 일반 표현 사용, 최종 보고 "확인 필요"
- 반복 틀: "물·그늘·휴식"

| No | 파트 | archetype(변형) | 제목 | 핵심 메시지 | 단계 | 사실 |
|---|---|---|---|---|---|---|
| 01 | 표지 | cover | 폭염 작업 안전 | - | 0 | - |
| 02 | 순서 | agenda | 오늘 이야기할 네 가지 | 위험 → 규정 → 조치 → 확인 | 5 | - |
| 03 | ① 위험 | timeline | 폭염 피해는 해마다 늘고 있습니다 | 최근 몇 년 온열질환 추이 | 3 | F01, F02 |
```

슬라이드를 쓰기 전 점검:
- [ ] 파트 질문이 청중 입장의 질문이고, 제목이 모두 `expression.md` 1절 제목 유형 중 하나다(이름표 제목 없음)
- [ ] 같은 아키타입 4장 연속 없음(예시 묶음 제외), 퀴즈 수·위치가 3절 기준에 맞다. 확인 문제(check)가 파트 끝마다 있고, `data-review` ↔ `data-key` 열쇠가 짝 맞는다
- [ ] ①의 번호 체계가 ②·정리에서 이어지고, 반복 틀이 ③·checklist·closing 에 나온다
- [ ] 숫자가 들어가는 장마다 사실 id 가 있고, 그 사실은 원문대조·두출처일치다
- [ ] 예시가 청중의 실제 업무물이고, 조직 고유 정보는 확인됐거나 일반 표현으로 처리했다
- [ ] 장 수가 시간에 맞다

## 8. 덱 부속 데이터 (두 경로 공통, deck.json 선택 키)

덱을 혼자 볼 사람(자습)을 위해 `deck.json` 에 두 선택 키를 넣을 수 있다. 없어도 덱은 동작한다(한 장 요약은 마무리 장에서, 용어집은 빈 안내로 시작).

```json
{
  "title": "…", "output": "….html",
  "summary": {
    "one_line": "한 문장 요약",
    "analogy": "전체를 한 비유로",
    "points": ["핵심 2~4줄"], "remember": ["오늘의 세 줄"],
    "try": ["이렇게 써 보면 좋은 것"], "caution": ["주의할 점"],
    "terms": ["핵심 용어(glossary 에 있는 것만 풀이가 붙는다)"]
  },
  "glossary": [
    {"term": "용어", "en": "English", "alias": "짧은 비유", "plain": "쉬운 풀이 한두 문장", "slide": 7}
  ]
}
```

- `summary` 는 인쇄(P)의 한 장 요약에 그대로 들어간다. 마무리 장 알약·규칙 장 제목과 같은 문장을 되풀이하지 말고 그대로 하나로 쓴다.
- `glossary` 는 용어집(G)의 재료다. 5~12개가 적당하고, `slide` 는 그 용어를 설명한 장 번호(1부터). 없으면 본문 찾기로 그 장으로 간다.
- 두 키는 선택이다. 짧은 덱(15장 안팎)이나 발표 전용이면 넣지 않아도 된다. 다만 새 팩은 legacy 마무리 클래스에서 요약을 추출하는 방식에 기대지 않도록 `summary`·`glossary`를 명시하는 것을 권장한다.
